## 1. Executive summary

- **`crowd_fields` is a clean, scene-agnostic, pure-NumPy primitives layer — verified.** No `bpy` import; only `math`, `dataclasses`, `typing`, `numpy`. The "scene-agnostic, pure numpy, no bpy" claim (kb §1) is TRUE.
- **Engine verdict — WRAP (engine as a whole), with three primitives ABSORB as-is.** `FieldSpec` + `evaluate_fields` + `relax` + `ramp_env/decay_env/event_env` + `playback_rate` are production-quality and map cleanly onto design §6.4 (force fields) + §6.3 (local avoidance complement) + §8.3 (blend tree) + §11.4 (cache reading). `dominant_attractor` and `advance_phase` need a thin adapter for design v1.1's per-agent semantics and seconds-based clip_phase respectively.
- **`relax` is COMPLEMENTARY to ORCA, not a substitute.** It is vectorized Jacobi PBD with fixed iter count — handles hard penetration constraints (post-ORCA cleanup), but provides NO velocity-space avoidance (ORCA half-planes). The design v1.1 still needs NumPy ORCA implementation (§6.3); `relax` becomes the §6.3 fallback / residual-overlap solver.
- **`crowd_agents.py` and `crowd_fields` are REDUNDANT.** Both implement (a) a 2 m uniform hash grid, (b) personal-space separation, (c) gait phase — but with different APIs and different math (crowd_agents.py uses scalar soft-force + time-driven phase + Python loop; crowd_fields uses vectorized PBD + displacement-driven phase + NumPy). crowd_fields does NOT supersede crowd_agents.py — it supersedes the LATTER'S primitives; the zombie FSM (states, transitions, scenario tables) migrates as a scenario plugin that USES crowd_fields primitives.
- **`crowd_fields` is NOT used by the previz repo.** Grep confirms zero `from crowd_fields import` or `import crowd_fields` references in `/home/sync/blender-escape-previz/scripts/`. The engine's only client is its own test file (`scripts/test_crowd_fields.py`). It is greenfield code awaiting its first integration.
- **Tests verify correctness but NOT performance.** The kb's "~0.3 ms/tick at N=129" is a docstring claim (line 269) — `test_crowd_fields.py` measures no timings. Test #9 (`bit-identical`, 60 agents) + test #10 (`residual small`, 40 agents × 30 iters) prove determinism + convergence quality. Coverage gaps: no test of `dominant_attractor` with overlapping-active attractors (the strength-tiebreak path at line 187-188); no test of `relax` with mixed pair + disc interactions; no test of `event_env`'s release tail beyond `t_off + 0.4`.
- **`prop_carry` is NOT a crowd-sim concern.** It is a Blender-side prop-anchoring module (law 110) for carrying animated props (rifles, etc.) through scene timelines — useful only as a scenario plugin for crowd shots where agents carry props. Design v1.2 should reference it under §11.1 (Blender integration → "scenario plugins"), not §6/§8.

## 2. Per-primitive audit

### 2.1 `FieldSpec` (dataclass)

1. **What it does** (lines 59-92): Frozen dataclass describing one signed influence field. Encodes center (static or animated via `center_fn`), radius, signed strength, smooth/linear falloff, activation window `t_active`, optional `merge_obstacle` flag (also feed disc to relax), `strength_fn` (temporal envelope), and a `strength_repr()` method for hashable canonical serialization.
2. **API surface**: `FieldSpec(name, kind, radius, strength, falloff="smooth", center=None, center_fn=None, t_active=(0.0,45.0), merge_obstacle=False, source="", strength_fn=None)`; methods `strength_at(t) -> float`, `strength_repr() -> str`. `kind ∈ {"attract","repel","obstacle"}` is informational only — the SIGN of `strength_at(t)` decides direction (test #3 verifies kind="repel" + strength=-2.0 pushes away; kind="attract" + positive strength pulls toward center).
3. **Algorithm**: None (dataclass). `_center_of(f, t)` (line 95) resolves center vs center_fn with a fail-closed `ValueError` if neither is set — important guard.
4. **Performance**: N/A (dataclass). One Python-level lookup per field per tick.
5. **Determinism**: Frozen + hashable. `strength_fn` is a closure with `__qualname__` set canonically (lines 208, 218, 234) — so two `ramp_env(1,2,post=3.0)` calls produce identical `strength_repr()`. Hashable.
6. **Tested behaviors**: Construction in tests #2-#8; `strength_fn` REPLACES static strength (test #4); `merge_obstacle=True` feeds disc (test #5); `t_active` gating (test #5). **Gap**: no test that `center_fn` actually fires (only `center=(...)` static is tested for the math branches); no test of `_center_of` raising on neither-set.
7. **Design v1.1 fit**: Maps to §6.4 `ForceField` dataclass — but the design's `ForceField` has different fields (`type: ForceFieldType` enum with `ATTRACTION/REPULSION/DANGER/FLOW`; `source_object: Optional[str]`; `region: Optional[AABB]`; `falloff: FalloffProfile` enum LINEAR/QUADRATIC/CUBIC/STEP; `strength` in **m/s²** vs kit's **m/s**; `time_horizon: Optional[float]`). The design's `source_object` (Blender object name) and `region: AABB` have NO kit equivalent — they need to be resolved at author time into a `center/center_fn`.
8. **Verdict**: **WRAP**. The kit's `FieldSpec` is cleaner (animated `center_fn`, temporal envelopes via `strength_fn`, hashable `strength_repr`) than the design's `ForceField`. Add a thin adapter `ForceField → FieldSpec` that resolves `source_object` to a `center_fn` (via the scene's object track) and reinterprets `strength` units. The design should ADOPT kit's `m/s desired-velocity` semantics (simpler, integrates directly into `evaluate_fields`) rather than `m/s²` acceleration.
9. **Gap analysis**: Design's `DANGER` and `FLOW` types are not expressible in kit — `DANGER` could map to `kind="repel"` + high strength; `FLOW` (directional wind) has no kit equivalent (kit fields are radial, not directional). Add a `direction: Optional[tuple[float,float]]` field for FLOW in v1.2 — that's a small REFACTOR.

### 2.2 `evaluate_fields` (function)

1. **What it does** (lines 106-158): Vectorized per-tick force accumulator. For each active field: compute distance from each agent to field center, skip agents outside `radius`, apply smooth `(1-(d/R)²)²` or linear `(1-d/R)` falloff scaled by signed strength, accumulate `(fx, fy)` arrays. Also collects `discs` (cx, cy, r) for any obstacle/merge_obstacle field.
2. **API surface**: `evaluate_fields(px, py, t: float, fields: Sequence[FieldSpec]) -> (fx, fy, discs)`. `px, py` are (N,) arrays; returns (N,) float arrays + `list[tuple[float,float,float]]`. Empty `fields=[]` returns `(zeros, zeros, [])` — verified by test #1.
3. **Algorithm**: Pure NumPy. Per-field Python loop over `fields` (typically ≤50 fields in a scene); per-field math is fully vectorized over agents (`np.hypot`, `np.where`, `np.maximum`). Skips fields with `not inside.any()` (line 147) — early exit when no agent is in range.
4. **Performance**: Vectorized over agents; Python-level loop over fields. For typical N=1000 agents × 50 fields, ~50 NumPy ops per tick — well under 1ms. The "0.3 ms/tick at N=129" kb claim is plausible but UNVERIFIED (no test measures it).
5. **Determinism**: Pure functions, no RNG, no global state. Deterministic by construction.
6. **Tested behaviors**: Tests #1-#5 cover empty table, smooth falloff value at known points, near-center, outside-skip, repel sign + linear value, strength_fn REPLACES static, t_active gating, obstacle disc, merge_obstacle. **Gap**: no test of multiple active attractors summing; no test of `center_fn` (animated) path; no test of `falloff="linear"` near edge (`d → R⁻`); no test of NaN propagation when `d = 0` (the `np.maximum(d, 1e-6)` guard is untested at the boundary).
7. **Design v1.1 fit**: Direct fit for §6.4 phase 6 (Steer): "compute the (N,2) acceleration tensor and add to preferred velocity." Design says fields are "evaluated vectorised" — kit already is. The unit mismatch (m/s vs m/s²) is a documentation fix, not an algorithm change.
8. **Verdict**: **ABSORB**. The algorithm is correct, vectorized, tested, and matches the design's phase-6 intent. One-line adapter to consume design's `ForceField` (after the §2.1 wrap).
9. **Gap analysis**: Design expects fields can modify `desired_velocity` directly (preferred velocity blending) — kit's output is a force/desired-velocity hybrid. The design's §6.4 also mentions `DANGER` (catastrophic-avoidance, immediate stop) and `FLOW` (directional wind) — neither is in kit. `FLOW` especially needs a non-radial formulation (a uniform vector field with a region mask) — small extension.

### 2.3 `dominant_attractor` (function)

1. **What it does** (lines 161-192): For each agent, computes the distance to the **single globally-strongest active attract field**. Returns `(best_d: (N,), best_idx: int)`. The alert-transition predicate helper — "ALERT iff d_i < eff_trigger_i".
2. **API surface**: `dominant_attractor(px, py, t, fields) -> (distances, winning_field_index)`. Note `best_idx` is a SCALAR (the global winner), NOT a per-agent array.
3. **Algorithm**: Python loop over `fields`, keeping only `kind=="attract"` fields with positive strength within `t_active`. Tracks the global max-strength field; once chosen, computes per-agent distance to that single field. Tiebreak: earlier field wins (line 187-188).
4. **Performance**: O(N × num_active_attract_fields). Cheap.
5. **Determinism**: Stable iteration order + explicit tiebreak → deterministic.
6. **Tested behaviors**: Test #6 covers three disjoint activation windows (window-a, window-b, none). **Gap**: NO test of overlapping-active attractors with the strength-tiebreak path. The current behavior (single global winner) is **wrong for the per-agent case**: if two attractors A (strength 3, far from agent i) and B (strength 2, near agent i) are both active, agent i reports distance to A (the global winner), even though B is the relevant attractor for i. The docstring even acknowledges this ("With disjoint activation windows (the common table shape) the argmax is trivial") — but the per-agent variant is what the design v1.1 §7.3 commuter example needs (utility-score + probability).
7. **Design v1.1 fit**: Design §7.3 behavior graph + §3.4 IR nodes (e.g., `IsDestinationCongested`, `PickAlternateDestination`) imply PER-AGENT goal selection. The kit's global-winner API is too coarse.
8. **Verdict**: **WRAP**. Keep the function for the alert-transition use case (zombie port: single dominant threat); add a sibling `per_agent_attractor(px, py, t, fields) -> (distances, indices)` that returns `(N,)` indices via a vectorized argmax. The vectorization is straightforward (stack per-field strengths as a (K,N) array, argmax along axis 0).
9. **Gap analysis**: No support for utility-score selection (the design v1.1 §7.3 mentions "utility-score + probability"). For v1, the simple per-agent argmax is enough; utility scores defer to M2+.

### 2.4 `ramp_env`, `decay_env`, `event_env` (temporal envelopes)

1. **What they do** (lines 199-235): Three closed-form scalar envelope builders. `ramp_env(t0, t1, post=1.0)` = 0 → post linearly over [t0,t1], flat outside. `decay_env(t_event, half_life)` = exponential decay from 1.0 at `t_event` (0 before). `event_env(t_on, t_off, attack=0.03)` = bounded pulse: fast attack from `t_on`, hold 1.0, exponential release after `t_off` (half-life 0.15s, tail cut at `t_off + 0.4`).
2. **API surface**: All three are `(*params) -> Callable[[float], float]`. Each sets `env.__qualname__` canonically (lines 208, 218, 234) for hashable serialization.
3. **Algorithm**: Closed-form scalar math; no deps. `decay_env` and `event_env` use `math.exp(-math.log(2.0) * dt / half_life)` (standard exponential half-life).
4. **Performance**: O(1) per evaluation. Pure Python scalar; if hot-loop needed, would need NumPy port (a `np.interp` + `np.where` formulation).
5. **Determinism**: Closed-form, deterministic.
6. **Tested behaviors**: Test #12 covers `decay_env` pre + half-life, `event_env` off + on + decay tail. `ramp_env` covered indirectly in test #4. **Gap**: `event_env`'s tail cut at `t_off + 0.4` is arbitrary and untested beyond `t=1.35` (test #12); no test that `event_env` returns 0 for `t > t_off + 0.4` (the explicit branch at line 227).
7. **Design v1.1 fit**: Design §6.4 mentions `time_horizon: Optional[float]` for FLOW but does NOT specify temporal envelopes for field strength. The kit's envelope primitives FILL this gap — they should be referenced in §6.4 as the canonical strength-modulation mechanism.
8. **Verdict**: **ABSORB**. Clean, tested, no deps. Direct fit for any time-varying force field (a siren that ramps up, a muzzle strobe that pulses, a threat that decays).
9. **Gap analysis**: No ENVELOPE for periodic/looping strength (e.g., a pulsing beacon at 2 Hz). Add `pulse_env(t_on, period, duty_cycle)` in v1.2 if needed — defer unless a scenario demands it.

### 2.5 `relax` (function — the PBD solver)

1. **What it does** (lines 242-367): In-place vectorized PBD pass for personal space + static obstacle discs. Computes pair set via spatial hash + grouped-join, runs `iters` Jacobi iterations: per-iter, computes per-pair push vectors along centerline, accumulates with `np.add.at` (order-independent scatter), applies `pos += push` once per iter. Static discs are infinite-mass (agent pushed fully out; disc never moves).
2. **API surface**: `relax(pos, radii, iters=3, discs=(), *, cell=2.0, eps=1e-4) -> None`. `pos: (N,2) float64 MODIFIED IN PLACE`; `radii: (N,)`; `discs: Sequence[(cx,cy,r)]`. Returns None.
3. **Algorithm**: **Vectorized Jacobi PBD** with fixed iteration count (no convergence criterion). Pair set built ONCE before the iter loop (line 276-331); each iter recomputes overlaps against current positions but applies all corrections simultaneously (`pos += push` at line 367, NOT in-place per-pair). Spatial hash: `cell = max(cell, 2 * max(radii))`; grouped-join via `np.argsort + searchsorted + np.repeat` to expand cell-pair matches into (i, j) index arrays. The 4 directional offsets `(0,1), (1,-1), (1,0), (1,1)` visit each unordered cell-pair exactly once (line 312). Final `lexsort` on `(pi, pj)` pins canonical order (line 327) — though `np.add.at` is order-independent regardless, the deterministic order is belt-and-braces for STRICT mode.
4. **Performance**: The docstring + kb claim "~0.3 ms/tick at N=129" — the inline comment at line 269 says the pre-fix Python bucket loop was "~1.0 ms/tick at N=129 vs the 0.4 ms budget", and the vectorized grouped-join was the fix. **No test measures timing**. For 1K agents (the design v1.1 gate), expect ~5-15ms/tick (linear in pair count, ~5K-10K pairs at 0.45m radius in 2m cells). Scaling: O(N + pairs) per iter; pair count is O(N × density × cell_area). Will NOT scale to 10K without spatial-index upgrade (quadtree/BVH).
5. **Determinism**: Stable `argsort(kind="stable")` + canonical `lexsort` + `np.add.at` (order-independent scatter) → bit-identical runs. Test #9 (`bit-identical`, 60 agents, default_rng(7)) verifies this directly. The design v1.1 §4.4 STRICT mode requires "discrete decisions: exact match" — relax satisfies this for the position-projection step.
6. **Tested behaviors**: Test #7 (overlap resolution, 2 agents), test #8 (static disc infinite mass), test #9 (determinism, 60 agents), test #10 (convergence-quality, 40 agents × 30 iters → residual ≤ 0.02m). **Gap**: no test with mixed pair + disc interactions (an agent squeezed between another agent and a disc — the degenerate-axis case at line 363 is untested); no test of large `iters` (e.g., 12, the iCrowds upper bound); no test of `cell` parameter override; no test of zero-agent edge case (line 263 `if n == 0: return`); no test of all-same-position agents (the degenerate-center case).
7. **Design v1.1 fit**: Design §6.3 (NumPy ORCA) is the primary local-avoidance layer. `relax` is **complementary**: ORCA produces velocity-space avoidance (anticipatory, no penetration if everyone cooperates); `relax` produces position-space separation (hard penetration cleanup). AAA systems (bgyss, Houdini Crowds, Golaem) typically run ORCA + a PBD/separation post-pass. The design v1.1 does NOT explicitly call out this complement — §6.3 says ORCA alone.
8. **Verdict**: **ABSORB** as a §6.3 post-pass (Phase 6.5: "PBD penetration cleanup after ORCA"). NOT a substitute for ORCA. The kit's relax is correct, tested, deterministic, and the pair-set grouped-join is genuinely clever (worth keeping for any future spatial-hash code).
9. **Gap analysis**: No support for MOVING obstacles (only static discs). Design §6.3 ORCA handles moving neighbor avoidance; relax's discs are infinite-mass static — moving OBBs (the jeep in zombie-escape) need a separate path OR a per-tick re-positioned disc (kit supports this via per-tick `discs` arg, but disc velocity is not propagated to the agent). Document this as a v1.2 limitation.

### 2.6 `advance_phase` (function — gait phase)

1. **What it does** (lines 374-380): Scalar function: `phase = (phase + disp / stride) % 1.0`. Drives gait phase by ROOT DISPLACEMENT (not time) — the foot-slide killer.
2. **API surface**: `advance_phase(phase, disp, stride) -> float`. Scalar in, scalar out. Returns input unchanged if `stride <= 0` (line 378-379).
3. **Algorithm**: Trivial modulo. No deps.
4. **Performance**: O(1) per agent per tick. NOT vectorized — would need a `np.mod(phase + disp / stride, 1.0)` one-liner for the hot loop.
5. **Determinism**: Closed-form, deterministic.
6. **Tested behaviors**: Test #11 covers `advance` (0.9 + 0.3/1.0 → 0.2) and `zero stride safe` (returns 0.5 unchanged). **Gap**: no test of negative `disp` (walking backwards — should still advance phase, but does it?); no test of very large `disp` (multiple wraps in one tick — should still be correct due to `% 1.0`); no test that phase stays in `[0, 1)`.
7. **Design v1.1 fit**: **MISMATCH.** Design §4.2 explicitly switched `clip_phase` from normalized `[0,1]` to **SECONDS since clip start** (per audit A2: "wrap-safe linear interp across loop boundary"). Kit uses normalized `[0,1]` phase. The two formulations are mathematically equivalent (`phase_secs = phase_norm × clip_duration`) but the API contract differs.
8. **Verdict**: **WRAP**. Add `advance_phase_secs(phase_secs, disp, clip_duration) -> float` that returns `(phase_secs + disp / stride * clip_duration) % clip_duration`. Keep the kit's normalized version for legacy/interchange. Alternatively, REFACTOR kit to take an optional `clip_duration` param (defaults to 1.0 for backward compat).
9. **Gap analysis**: Kit's `stride` parameter is "metres per full gait cycle" — design should clarify this is `clip_duration × nominal_speed` (e.g., a 1.0s walk clip at 1.35 m/s nominal → stride = 1.35m). The kit's docstring says "driven by root DISPLACEMENT, never time" — this is the right invariant; design v1.1 §8.3 should explicitly cite this law.

### 2.7 `playback_rate` (function — gait playback rate)

1. **What it does** (lines 383-387): Scalar function: `clip(speed / nominal, lo=0.5, hi=2.0)`. Returns 1.0 if `nominal <= 0` (safe default).
2. **API surface**: `playback_rate(speed, nominal, *, lo=0.5, hi=2.0) -> float`. Scalar in, scalar out.
3. **Algorithm**: `np.clip` (one-liner).
4. **Performance**: O(1) per agent per tick. NOT vectorized — but trivially so (`np.clip(speed / nominal, lo, hi)` on (N,) arrays).
5. **Determinism**: Closed-form, deterministic.
6. **Tested behaviors**: Test #11 covers `rate clamp lo` (0.2 → 0.5), `rate clamp hi` (9.0 → 2.0), `rate nominal` (1.0 → 1.0). **Gap**: no test of `nominal <= 0` (the safe-default branch at line 385-386); no test of negative `speed` (walking backwards — should the rate be negative? Kit clamps to lo=0.5, which would play the clip forward at half speed — probably wrong for backwards motion).
7. **Design v1.1 fit**: Direct fit for §4.2 `playback_rate` buffer + §8.3 "blend weights compute at runtime per agent based on `velocity` and `orientation` deltas." The [0.5, 2.0] clamp range matches the design's "outside the clamp you switch clips, never skate" semantics.
8. **Verdict**: **ABSORB**. Trivial, correct, tested. Vectorize as a one-liner for the hot loop.
9. **Gap analysis**: The clamp range [0.5, 2.0] is hardcoded — should be a per-clip parameter (a jog clip might allow [0.7, 1.3] for natural variation; a walk clip might allow [0.5, 2.0]). The design's `Clip` dataclass (§8.1) should carry a `playback_rate_range: Tuple[float, float]` field; `playback_rate()` already accepts `lo`/`hi` kwargs — compatible.

### 3.1 API stability (question 10)

### 3.2 Scene-agnostic claim (question 11)

### 3.5 Overlap with `crowd_agents.py` (question 14)

**REDUNDANT — but at the PRIMITIVES level, not the system level.** crowd_agents.py reimplements three of crowd_fields' primitives with different APIs and different math:

| Primitive | crowd_agents.py | crowd_fields.py | Same algorithm? |
|---|---|---|---|
| Uniform 2m hash grid | `_grid_build` (line 140, `int(x//2), int(y//2)`) | `relax` spatial hash (line 276, `np.floor(pos/grid)`) | YES — same cell size, same key. Kit is vectorized + grouped-join; previz is Python dict. |
| Personal-space separation | `_active_step` lines 261-277: soft force `(1-d/R)/d` + 3× weight if `d < SEP_HARD` | `relax` lines 335-367: PBD position projection, `overlap/2 + eps` per iter | NO — different paradigms. Previz is soft force (continuous, can stabilize at residual overlap); kit is hard PBD (positional, exact separation after enough iters). Kit is more correct for "no penetration" gates. |
| Gait phase | `gait_phase = rng.uniform(0, 2π)` (line 106) + `swing = sin(2π × gait_f × t + phase)` (line 227) — TIME-driven | `advance_phase(phase, disp, stride)` — DISPLACEMENT-driven | NO — different invariants. Previz ties gait to time (foot-slide if speed varies); kit ties to displacement (foot-slide-free by construction). |

**Crowd_fields does NOT supersede crowd_agents.py — it supersedes the LATTER'S PRIMITIVES.** The zombie FSM (9 states, transition logic, OBB pushout, scenario tables) is scenario logic that must migrate as a scenario plugin which USES crowd_fields primitives. Migration path: in design v1.2's Phase 2 (zombie port), the new `crowd/scenarios/zombie_escape.py` plugin should call `crowd_fields.relax()` for separation, `crowd_fields.advance_phase()` for gait, and `crowd_fields.evaluate_fields()` for the hero/jeep attractor fields — replacing the inline implementations in `crowd_agents.py:140-277,227-240`.

## 5. Top 5 concrete design v1.2 revisions (ranked by impact)

1. **§6.3 — Add a "PBD penetration cleanup" post-pass after ORCA.** Insert a new §6.3.1 immediately after the ORCA LP description: "After ORCA solves the velocity-space avoidance, run `crowd_fields.relax(pos, radii, iters=3, discs=obstacle_discs)` to resolve any residual positional penetrations ORCA's velocity solution left (e.g., when a high-density cluster or a dynamic obstacle shoves an agent into a neighbor). This is the standard ORCA + PBD complement pattern (bgyss, Houdini Crowds, Golaem). The kit's `relax` is vectorized Jacobi PBD with deterministic pair-set ordering (spatial hash + grouped-join + lexsort); `iters` is the quality knob (1-12, default 3)." **Impact**: closes the biggest gap in the v1.1 avoidance story (ORCA alone does not guarantee zero penetration under dense constraints).

2. **§6.4 — Replace the `ForceField` dataclass with `crowd_fields.FieldSpec` (or document the adapter).** Either (a) swap the design's `ForceField` for the kit's `FieldSpec` directly (cleaner, already tested, already hashable), OR (b) keep `ForceField` as the authoring-time schema and add an explicit "ForceField → FieldSpec adapter" subsection that resolves `source_object` (Blender object name) to a `center_fn` (reads the object's animated world position), reinterprets `strength` from m/s² to m/s (desired-velocity at center, the kit's semantics), and translates `type=ATTRACTION/REPULSION/DANGER` to `kind="attract"/"repel"/"repel"` (DANGER = high-strength repel). Add `direction: Optional[tuple[float,float]]` to FieldSpec for the FLOW case (deferred to M3+). **Impact**: eliminates a redundant dataclass; adopts the kit's cleaner API; makes the kit's tests the design's tests.

3. **§6.4 — Add temporal envelopes as the canonical strength-modulation mechanism.** Insert after the ForceField/FieldSpec reconciliation: "Force-field strength is modulated over time via temporal envelopes attached to `FieldSpec.strength_fn`. The kit ships three (kit primitives, see kb/crowd_fields.md): `ramp_env(t0, t1, post=1.0)` for power-up ramps, `decay_env(t_event, half_life)` for transient repulsors (siren, explosion), `event_env(t_on, t_off, attack=0.03)` for bounded pulses (muzzle strobe, door slam). `FieldSpec.strength_repr()` produces a canonical hashable description — params hashes stay honest across sim reruns." **Impact**: fills a gap the v1.1 design leaves open (time-varying fields are mentioned but not specified).

4. **§8.3 + §4.2 — Reconcile `clip_phase` units (seconds vs normalized) and adopt kit's displacement-driven gait law.** Either (a) keep the design's seconds-based `clip_phase` and add a thin wrapper `advance_phase_secs(phase_secs, disp, clip_duration)` (or refactor `advance_phase` to take optional `clip_duration=1.0`), OR (b) revert the design to normalized [0,1] phase and use the kit's `advance_phase` directly. Either way, add an explicit LAW: "gait phase is driven by root DISPLACEMENT, never time (kit law, kills foot-slide by construction); `playback_rate = clip(speed / nominal, lo, hi)` clamped per-clip." Add `playback_rate_range: Tuple[float, float] = (0.5, 2.0)` to §8.1 `Clip` dataclass. **Impact**: resolves the audit-A2 normalized-vs-seconds ambiguity with a clear invariant; adopts the kit's displacement-driven law as a design principle.

5. **§11.4 — Reference `iter_all_fcurves()` (not just `iter_fcurves()`) for read-only consumers, and add a §11.5 "Scenario plugins" subsection referencing `prop_carry`.** Change line 963 from "the existing `iter_fcurves()` shim (which only handles reading)" to "the existing `iter_fcurves()` shim (write-side: returns slot[0]'s collection for `.new()`/`.find()`) and `iter_all_fcurves()` (read-side: chains EVERY slot's channelbag, required for 5.x multi-slot actions like a mesh's Key datablock sharing the object's auto-named action)." Add new §11.5: "Scenario plugins: for shots where crowd agents carry props, use the kit's `blender_kit.prop_carry` module (law 110) for ALL carried-prop keyframing — never raw `keyframe_insert`. The crowd bake must not violate LIVE-READ / SAME-FRAME / FULL-TIMELINE / SANITY-RADIUS." **Impact**: brings the design's Blender-integration section up to date with the kit's current 5.x shims; clarifies that prop-carry is a shot-level concern, not a crowd primitive.

## 6. Open questions for the orchestrator

1. **ORCA + relax ordering**: should `relax` run (a) every tick after ORCA (defensive, ~5-15ms/tick cost at 1K), (b) only when ORCA reports a penetration (event-driven, near-zero amortized cost), or (c) only at bake-resolution frames (cheaper, may miss intra-tick penetrations)? The kit's `relax` is cheap enough for (a) at 1K, but the design's 33ms FAST budget is tight — profile in M0.
2. **`FieldSpec` vs `ForceField` — adopt or adapter?** Option (a) is cleaner (one dataclass, kit's tests become the design's tests) but breaks the design's `source_object`/`region` authoring API. Option (b) keeps the design's authoring schema but adds an adapter layer (more code, more docs). Recommendation: (b) for v1.2 — the adapter is ~30 lines and keeps the design's authoring UX clean.
3. **Per-agent argmax for `dominant_attractor`**: is the per-agent variant needed in v1, or defer to M2 with the typed blackboard? The commuter example (§7.3) implies per-agent; the zombie port (Phase 2) only needs the global variant. Recommendation: ship the global variant in v1 (kit as-is); add the per-agent variant in M2 with the behavior-graph utilities.
4. **FLOW field type**: the design's `ForceFieldType.FLOW` (directional wind, not radial) has no kit equivalent. Defer FLOW to M3+ (the design already says "FLOW defer to M3+"), OR add a `direction: Optional[tuple]` field to `FieldSpec` in v1.2 (small extension, ~10 lines).
5. **`advance_phase` units**: which path — (a) keep kit's normalized [0,1] and revert design v1.1's audit-A2 change, or (b) keep design's seconds and add `advance_phase_secs`? Recommendation: (b) — seconds-based is more flexible (variable-duration clips, sub-frame interpolation); the wrapper is 5 lines.
6. **`relax` moving-obstacle support**: the kit's `discs` arg is per-tick (positions can change between calls), but disc VELOCITY is not propagated to the agent. For the zombie-escape jeep (a moving OBB), this means relax can push agents out of the jeep's current footprint but cannot anticipate the jeep's next-tick position — ORCA must handle that. Is this acceptable for v1, or does the jeep need a dedicated OBB-avoidance primitive (the previz `crowd_agents.py:_obb_pushout` pattern, generalized)?
7. **`crowd_fields` API stability vs v1.2 design lock-in**: the kit's API was last refined in "session-26" (recent). If v1.2 ABSORBS `FieldSpec` + `evaluate_fields` + `relax` as kit-level primitives (recommended), the design now depends on their stability. Should the design v1.2 explicitly state "crowd_fields is the kit-level primitives layer; the crowd system treats its API as stable from v1.2 forward"? Recommendation: yes — makes the dependency explicit and lets future refactors proceed with deprecation paths.
8. **`prop_carry` and crowd-system bake**: if a crowd shot has agents carrying props (e.g., a riot scene with banners), the bake must produce per-agent carry tracks that satisfy law 110. Does the design v1.2's cache format (§9.2) need a `carry_state` channel (per-agent, per-tick: which prop, which anchor), or is this purely a scenario-plugin concern that lives in the shot's `apply_patch` layer? Recommendation: defer to M3+ — the cache stores `clip_id + clip_phase` only; prop-carry is a shot-level keyframe layer on top.
